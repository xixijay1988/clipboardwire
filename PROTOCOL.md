# clipboardwire — wire protocol v0.4

This document specifies the protocol between a clipboardwire **client** and the
clipboardwire **server**. It is the only contract between the two halves; either
side can be reimplemented in any language as long as this document is honored.

Version: **0.4** (unstable; will break until 1.0).

### Changes since v0.1

- `clip` frames may now carry **binary** payloads via a new `content_b64`
  field (base64 of opaque bytes). `content` and `content_b64` are mutually
  exclusive within a single frame.
- `content_type` is no longer restricted to `text/plain; charset=utf-8`:
  v0.2 servers and clients additionally support `image/png`. Other MIME
  types are forward-reserved; servers must not close the connection on
  unknown types — they relay the frame and let clients decide.
- Default max frame size raised from 10 MiB to **50 MiB** to fit
  screenshot-sized PNGs without operator tuning.

### Changes since v0.3

v0.3 shipped file transfer as a **push**: the sender read the whole file and
broadcast every chunk. v0.4 adds a **lazy** path where the source announces a
file and only reads the bytes somebody actually asks for. Both remain on the
wire; a peer declares which it can do through `caps` (§2.1).

- **Nine frame types**, up from four (`clip`, `welcome`, `error`, `file_chunk`).
  New: `file_offer`, `file_pull`, `file_digest`, `file_abort`, `peer_changed`
  (§3.4, §3.5, §3.7–§3.9); `file_chunk` gained the lazy shape (§3.6).
- **Device identity separate from connection identity.** A peer is now a
  `device_id` (stable across reconnects, generated by the client and sent as a
  `device` query parameter) as well as a per-connection `client_id`. Frames that
  address a peer use the device id, because only that survives a reconnect.
- **Capability negotiation via `caps`.** Clients advertise the query parameter
  `caps=`; the hub advertises `welcome.caps`. Both are token lists with a
  forward-compatible grammar (§3.2, §7).
- **`peer_changed`** replaces the implicit "reconnect and hope" model of
  membership: the hub now pushes joins and leaves.
- **`welcome` carries live offers** so a late joiner can pull a file copied
  before it connected.
- `file_chunk` gains optional `to`, `transfer_id` and `from_device` for directed
  delivery; its eager shape is unchanged byte-for-byte, so a v0.3 reader still
  parses a v0.4 eager chunk.

## 1. Overview

- Transport: **WebSocket** over HTTP/1.1. The server speaks `wss://` when
  built-in TLS is configured (cert + key env vars set), otherwise plain
  `ws://` — in which case a reverse proxy is expected to terminate TLS.
- Authentication: **HTTP Basic** on the upgrade request. One user, configured in the
  server's environment.
- Confidentiality: **transport-only.** TLS (built-in via rustls or via a
  reverse proxy) protects the wire; the server itself sees clipboard contents
  in plaintext. This is by design — see the README's threat-model section.
  There is **no** client-side encryption layer.
- Topology: star. The server is a dumb hub that fans out frames to all
  authenticated peers except the sender. There is no persistent state on disk.
  It is not entirely stateless in memory: it caches the last clip, the live
  offers, and a bounded set of transfer-session ids (§5).

## 2. Connection lifecycle

### 2.1 Handshake

1. Client opens a WebSocket to `ws://<host>:<port>/sync`.
2. The HTTP upgrade request **must** carry an `Authorization: Basic <b64>` header,
   where `<b64>` is `base64(user + ":" + password)` per RFC 7617.
3. The upgrade URL **may** carry two query parameters:
   - `device=<uuid>` — the client's stable device id. A pre-0.4 client omits it;
     the hub then falls back to the connection's own id, which means the peer is
     not addressable across a reconnect.
   - `caps=<token>[,<token>…]` — comma-separated capability tokens (§7). Values
     longer than `MAX_CAPS_BYTES` are ignored wholesale rather than truncated.
4. The server validates credentials using a constant-time comparison.
   - On failure the server responds with HTTP `401 Unauthorized` and the WebSocket
     is never opened. No body, no hints.
   - On success the server completes the upgrade (HTTP `101`).
5. Immediately after the upgrade succeeds, the server sends one `welcome` frame
   (see §3.2).

### 2.2 Steady state

After `welcome`, the connection is symmetric: either side may send frames at any
time. Frames are JSON-encoded WebSocket **text** frames, one JSON object per frame.

### 2.3 Keep-alive

The server sends a WebSocket **Ping** every 30 s. The client must reply **Pong**.
The server closes any connection that fails to pong within 10 s of a ping.
Clients should send Pings of their own if they don't see server traffic for 60 s
and reconnect (§2.5) if the server doesn't pong within 10 s.

### 2.4 Closure

Either side may close cleanly with code `1000`. Server-initiated error closures
use the codes in §6.

### 2.5 Reconnect

Clients must reconnect with exponential backoff: initial 1 s, doubling to a cap
of 60 s, with ±20 % jitter. The backoff resets to 1 s after a connection has been
open for at least 30 s.

A reconnect is a **new connection with the same device id** (§2.1). The hub keeps
the device's offers alive for a grace period after the connection goes away
(`DEVICE_GRACE_MS`, 60 s) so a transient drop does not make its files
unpullable. Re-advertising after a reconnect must **not** extend an offer's
expiry — the source re-sends its original `ts` and the original absolute
`expires_at_ms`.

## 3. Frame types

Every frame is a JSON object with a string field `type`.

**Unknown frame types are ignored, not refused.** The hub's reader drops any
inbound frame whose `type` it does not recognise — including types introduced by
a later protocol revision — logs at DEBUG, and keeps the connection open. This is
forward-compatibility with teeth: a deployed hub cannot be upgraded in step with
every client, and closing on an unrecognised frame would make every future
revision a flag day. Only a frame whose `type` cannot be read at all (bad JSON,
missing `type`, non-string `type`) is a `bad_frame` rejection (§6), because an
unidentifiable frame cannot be assumed to come from the future.

The one exception is direction: `welcome` and `error` are server-to-client, so a
client sending either is a protocol violation and is still refused.

### 3.1 `clip` — clipboard payload

Sent by either side. The publishing client wraps a clipboard change; the server
relays the *same frame body* to every other connected peer, adding a `from`
field. Each frame carries **exactly one** payload — either `content` (text)
or `content_b64` (binary), depending on `content_type`.

Text example:

```json
{
  "type": "clip",
  "id": "8c4a2e6e-7a3e-4d7c-9b1f-1d2e3f4a5b6c",
  "ts": 1716163200000,
  "content_type": "text/plain; charset=utf-8",
  "content": "the clipboard text, verbatim"
}
```

Binary example (PNG screenshot):

```json
{
  "type": "clip",
  "id": "11111111-2222-4333-8444-555555555555",
  "ts": 1716163210000,
  "content_type": "image/png",
  "content_b64": "iVBORw0KGgoAAAANSUhEUgAA..."
}
```

Field rules:

| Field          | Required        | Notes                                                                                                                                                                              |
| -------------- | --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`           | yes             | RFC 4122 UUIDv4, generated by the publishing client. Used for dedup.                                                                                                               |
| `ts`           | yes             | Unix epoch milliseconds at the publisher, used by clients to drop stale frames.                                                                                                    |
| `content_type` | yes             | MIME type of the payload. Known types: `text/plain; charset=utf-8` (uses `content`); `image/png` (uses `content_b64`). Other types are forward-reserved — relay opaquely.           |
| `content`      | conditional     | Required when `content_type` starts with `text/`. The clipboard text as a JSON string. Mutually exclusive with `content_b64`.                                                      |
| `content_b64`  | conditional     | Required when `content_type` is non-textual. Standard-alphabet base64 of the raw payload bytes (e.g. PNG file contents). Mutually exclusive with `content`.                        |
| `from`         | added by server | Server-assigned per-connection client id (UUID string). Clients should ignore frames where `from` matches their own id.                                                            |

The server *may* log frame `id`, `ts`, `content_type`, length, and `from` for
observability. It **must not** log `content` or `content_b64` at INFO level
or above.

A frame missing both `content` and `content_b64`, or carrying both, is
malformed: the server responds with `error` code `bad_frame` and close
`4002`. Clients should treat such frames identically if they ever receive
one from a misbehaving peer.

### 3.2 `welcome` — server greeting

Sent by the server exactly once, immediately after the upgrade.

```json
{
  "type": "welcome",
  "server": "clipboardwire/0.4.0",
  "client_id": "f0e9d8c7-b6a5-4321-9876-0123456789ab",
  "caps": ["lazy-file"],
  "peers": [
    { "device": "22222222-3333-4444-8555-666666666666", "caps": ["lazy-file", "file-recv"] }
  ],
  "offers": [],
  "last_clip": null
}
```

| Field       | Required        | Notes |
| ----------- | --------------- | ----- |
| `server`    | yes             | Build identifier, `clipboardwire/<major>.<minor>.<patch>`. **Diagnostic only** — see §7. |
| `client_id` | yes             | Per-connection id. The hub tags this connection's relayed frames with it in `clip.from`. A client uses it to recognise its own echoes. It does **not** survive a reconnect; `device` ids do. |
| `caps`      | optional        | Capability tokens this hub build supports. Absent means "nothing" — which is exactly what a pre-0.4 hub looks like, and what makes a mixed deployment fall back to eager transfer. |
| `peers`     | optional        | Every *other* currently connected peer, each with its device id and advertised capabilities. A snapshot: `peer_changed` keeps it current afterwards. |
| `offers`    | optional        | Every live offer at connect time, in full `file_offer` shape. This is how a late joiner learns about files copied before it arrived. Expired offers are swept before the snapshot is built. |
| `last_clip` | yes             | Either `null` or a complete `clip` frame (the most recent clip the server has cached). The client may decide whether to apply it. |

A hub that sends non-empty `offers` while omitting `lazy-file` from its own
`caps` is internally inconsistent; clients should log it and treat the hub as
capability-less rather than trusting the offers.

### 3.3 `error` — server-side soft error

```json
{ "type": "error", "code": "frame_too_large", "message": "max 52428800 bytes" }
```

Sent before a non-fatal disconnect, or to acknowledge a rejected frame without
closing the socket. Codes are the §6 strings.

### 3.4 `file_offer` — announce a file without sending it

Sent by a **source** client. It says "this file exists, is this big, and can be
pulled until this deadline". No bytes move.

The hub caches the offer under `(source device, file_id)` and answers the sender
with an `error{code: "bad_frame"}` frame if it refuses it (never a close — a bad
offer is the sender's mistake, not a protocol violation).

The hub also pushes the offer to every **already-connected** peer whose `caps`
include `lazy-file`, as a `file_offer` frame on that peer's routed-frame channel
— the sender itself is skipped. A peer that never advertised `lazy-file`
(including any pre-0.4 client, whose capability set is empty) receives nothing,
which is the hub's half of "SHALL NOT send them to peers that do not".
Offers additionally appear in `welcome.offers`, so a late joiner learns about
files copied before it connected.

A full routed-frame buffer drops the push for that one peer with a log line; the
offer stays cached and remains pullable, and reappears in `welcome.offers` on
that peer's next connection.

```json
{
  "type": "file_offer",
  "file_id": "3f1c9a52-7d4e-4b2a-9f1e-2c3d4e5f6a7b",
  "batch_id": "aa11bb22-cc33-4d44-8e55-ff6677889900",
  "ts": 1716163200000,
  "name": "report.pdf",
  "content_type": "application/pdf",
  "file_size": 5242881,
  "expires_at_ms": 1716165000000
}
```

| Field           | Required        | Notes |
| --------------- | --------------- | ----- |
| `file_id`       | yes             | UUIDv4 chosen by the source. Stable for the lifetime of one offer; reused when the same path is re-advertised with unchanged identity. Session-less. |
| `batch_id`      | yes             | Groups the files of a single copy/paste action. Pulls from the same batch share the source's concurrency budget instead of competing for it, so a five-file paste is not throttled to one file at a time. |
| `ts`            | yes             | Unix epoch ms when the source copied the file. Also the tie-breaker a receiver uses to ignore a stale re-advertisement. |
| `name`          | yes             | File name without directory components (≤ `MAX_OFFER_NAME_BYTES`). The receiver sanitises it before use as a path. |
| `content_type`  | yes             | Best-effort MIME type (≤ `MAX_OFFER_CONTENT_TYPE_BYTES`). |
| `file_size`     | yes             | Bytes. Must be ≥ 1; zero-byte files are never offered. |
| `expires_at_ms` | yes             | **Absolute** deadline in Unix ms, not a TTL. The source owns it: a hub restart or a reconnect does not restart the clock. Must be in the future and within `MAX_OFFER_TTL_MS` of the hub's clock. |
| `from_device`   | added by server | The offering device. The hub overwrites unconditionally; a client-supplied value is ignored, because it is unauthenticated and would let a peer impersonate another source. |

The hub enforces two caps on offers — `MAX_OFFERS_PER_DEVICE` and
`MAX_OFFERS_TOTAL` (§5). Exceeding either rejects the **new** offer; it never
evicts someone else's.

### 3.5 `file_pull` — ask the source for a window of chunks

Sent by a **receiver** client. Contains no payload.

```json
{
  "type": "file_pull",
  "file_id": "3f1c9a52-7d4e-4b2a-9f1e-2c3d4e5f6a7b",
  "transfer_id": "9d8c7b6a-5f4e-4d3c-2b1a-0987654321fe",
  "to": "55555555-6666-4777-8888-999999999999",
  "chunk_index": 0,
  "window": 8
}
```

| Field         | Required        | Notes |
| ------------- | --------------- | ----- |
| `file_id`     | yes             | Which offer to serve. Must name an offer owned by `to`. |
| `transfer_id` | yes             | The **session key**. One `transfer_id` names exactly one session and never two files, so reusing an open id for a different `file_id` is refused. |
| `to`          | yes             | **The source's `device_id`** — *not* the recipient. This is the single most counter-intuitive field in the protocol; see the note below. |
| `chunk_index` | yes             | 0-based. The **first** pull of a session must be `0`; a later window may start anywhere. |
| `window`      | yes             | How many chunks to return, `1..=MAX_PULL_WINDOW`. A larger window is refused with `file_abort{window_too_large}` rather than clamped. |
| `from_device` | added by server | **The puller's `device_id`.** The hub stamps it on relay and it is the only way the source learns where to address chunks, since `to` already names the source. |

> **`to` and `from_device` are inverted on purpose.** `FilePullFrame::to` means
> "who I am asking", so it carries the *source*. `FilePullFrame::from_device`
> means "who asked", so it carries the *puller*. The hub is the only writer of
> `from_device`: it overwrites whatever the client put there, because a
> client-chosen value is unauthenticated and would let a peer aim a file's bytes
> at an arbitrary device. A source that cannot see `from_device` must refuse the
> pull as `invalid_start`; guessing a recipient would leak the file.

A pull is authorized against the source's offer, and the hub relays it only if
the offer exists, has not expired, and the source has a live connection. Refusals
are answered at the **puller** (an abort addressed to the puller), never at the
source: see §3.8.

### 3.6 `file_chunk` — one slice of file bytes

Sent by the **source** client, addressed to one receiver (lazy) or broadcast
(eager). This frame has **two distinct shapes**, and validation dispatches on the
presence of `transfer_id`.

**Lazy shape** (`transfer_id` present — v0.4):

```json
{
  "type": "file_chunk",
  "file_id": "3f1c9a52-7d4e-4b2a-9f1e-2c3d4e5f6a7b",
  "name": "report.pdf",
  "content_type": "application/pdf",
  "chunk_index": 0,
  "total_chunks": 2,
  "file_size": 5242881,
  "payload_b64": "JVBERi0xLjQK...",
  "to": "77777777-8888-4999-aaaa-bbbbbbbbbbbb",
  "transfer_id": "9d8c7b6a-5f4e-4d3c-2b1a-0987654321fe",
  "from_device": "55555555-6666-4777-8888-999999999999"
}
```

**Eager shape** (no `transfer_id` — the v0.3 form, unchanged):

```json
{
  "type": "file_chunk",
  "file_id": "3f1c9a52-7d4e-4b2a-9f1e-2c3d4e5f6a7b",
  "name": "report.pdf",
  "content_type": "application/pdf",
  "chunk_index": 0,
  "total_chunks": 2,
  "file_sha256": "A1:B2:C3:…",
  "file_size": 5242881,
  "payload_b64": "JVBERi0xLjQK..."
}
```

| Field         | Required        | Notes |
| ------------- | --------------- | ----- |
| `file_id`     | yes             | Offer id. All chunks of one file share it. |
| `name`        | yes             | Non-empty, no NUL, no directory component. Repeats the offer's name so a mid-stream eager receiver can still label the file. |
| `content_type`| yes             | Best-effort MIME type. |
| `chunk_index` | yes             | 0-based; must be `< total_chunks`. |
| `total_chunks`| yes             | ≥ 1. `ceil(file_size / FILE_CHUNK_BYTES)`. |
| `file_sha256` | **eager only**  | Colon-separated uppercase hex SHA-256 of the whole file. Repeated in every eager chunk so a receiver that joined mid-stream can still verify. **Must be absent on lazy chunks** — there the hash travels in `file_digest` instead. |
| `file_size`   | yes             | Total file size in bytes. |
| `payload_b64` | yes             | Standard base64 of this chunk's raw bytes; decoded length ≤ `FILE_CHUNK_BYTES`, shorter for the last chunk. Non-empty. |
| `from`        | added by server | Per-connection client id. Kept for v0.3 compatibility; new code uses `from_device`. |
| `to`          | **lazy only**   | Destination `device_id`. **Forbidden on eager chunks**, which are broadcast. |
| `transfer_id` | **lazy only**   | Session key. Its presence is what selects the lazy validation rules. |
| `from_device` | added by server | Source `device_id`, stamped on relay. Never sent by a client. |

The two shapes are strictly separated, and each rule exists because the
alternative is a corrupt file:

| | eager (`transfer_id` absent) | lazy (`transfer_id` present) |
| --- | --- | --- |
| `file_sha256` | **required**, non-empty | **forbidden** |
| `to` | **forbidden** | **required** |
| Delivery | broadcast to every peer but the sender | directed at `to` only |
| Verification | the receiver checks each chunk's `file_sha256` at the end | the source sends `file_digest` after the last chunk; the receiver verifies against it |

A frame that mixes the shapes is malformed. Because the field set is ambiguous,
the hub closes the connection with `bad_frame`/`4002` rather than guessing which
shape was intended.

### 3.7 `file_digest` — the whole-file hash for one lazy session

Sent by the **source** client after the last chunk of a lazy transfer. It exists
only because a lazy chunk must not carry `file_sha256` (see §3.6): a receiver
cannot verify without the hash, and repeating it in every chunk would mean a
source that specced the file once now has to know it before the first byte.

```json
{
  "type": "file_digest",
  "file_id": "3f1c9a52-7d4e-4b2a-9f1e-2c3d4e5f6a7b",
  "transfer_id": "9d8c7b6a-5f4e-4d3c-2b1a-0987654321fe",
  "to": "77777777-8888-4999-aaaa-bbbbbbbbbbbb",
  "from_device": "55555555-6666-4777-8888-999999999999",
  "file_sha256": "A1:B2:C3:…"
}
```

| Field         | Required        | Notes |
| ------------- | --------------- | ----- |
| `file_id`     | yes             | Must match the session's file. A digest naming a different file is dropped. |
| `transfer_id` | yes             | The session it completes. |
| `to`          | yes             | Destination `device_id` — the receiver. |
| `from_device` | added by server | Source `device_id`, stamped on relay. |
| `file_sha256` | yes             | Colon-separated uppercase hex SHA-256 of the file. Must be non-empty. |

A digest for a session whose chunks are incomplete is answered by the receiver
restarting that transfer from index 0, not by verifying a partial file.

**A digest can be lost**, and the protocol is designed for it: the receiver's
routed-frame buffer is bounded, so a hub under pressure may drop a `file_digest`
(logged as a warning, not silently). The receiver's recovery is to re-request the
final window; the source answers a completed session with the digest again and no
chunks. For that to work the source must retain the session past the digest — it
does, until the idle timeout — which is why a source may re-emit a digest it has
already sent.

### 3.8 `file_abort` — end a transfer or invalidate an offer

Sent by either the **source** (a real abort) or the **hub** (a refusal on the
source's behalf). Contains no payload.

Scope is decided by `transfer_id`, **never** by `reason`.

**Session-scoped** (`transfer_id` present) — one receiver, `to` required:

```json
{
  "type": "file_abort",
  "file_id": "3f1c9a52-7d4e-4b2a-9f1e-2c3d4e5f6a7b",
  "transfer_id": "9d8c7b6a-5f4e-4d3c-2b1a-0987654321fe",
  "to": "77777777-8888-4999-aaaa-bbbbbbbbbbbb",
  "from_device": "55555555-6666-4777-8888-999999999999",
  "reason": "invalid_start"
}
```

**Offer-scoped** (`transfer_id` absent) — every holder of the offer; `to` may be
omitted to mean "all of them":

```json
{
  "type": "file_abort",
  "file_id": "3f1c9a52-7d4e-4b2a-9f1e-2c3d4e5f6a7b",
  "reason": "superseded"
}
```

| Field         | Required        | Notes |
| ------------- | --------------- | ----- |
| `file_id`     | yes             | The offer (and, if session-scoped, the file being transferred). |
| `transfer_id` | optional        | Present ⇒ session-scoped, and `to` becomes required. Absent ⇒ offer-scoped. |
| `to`          | conditional     | The recipient's `device_id`. **Required** when `transfer_id` is present; may be absent (broadcast) when it is not. |
| `from_device` | added by server | Source `device_id`, stamped on relay. |
| `reason`      | yes             | Non-empty. An **open** string set — see below. |

> **A broadcast abort is expanded by the hub, one copy per recipient.** When
> `to` is absent the source does not know (and should not need to know) who holds
> its offer. The hub fans the frame out to every peer except the sender and puts
> **each recipient's own `device_id` into `to`** on the copy that recipient
> receives. A receiver can therefore always trust `to` to name itself, and never
> has to decide whether a broadcast was meant for it. An offer-scoped abort the
> hub originates itself (a grace-period sweep after the source vanished) has no
> sender to skip, so every peer gets a copy.

**Known reasons** (the wire value is a free-form string; unknown values degrade to
"failed" at the receiver rather than being rejected):

| Reason            | Scope     | Meaning |
| ----------------- | --------- | ------- |
| `source_gone`     | offer     | The source disconnected past its grace period. |
| `superseded`      | offer     | The same path was re-copied with different content; the old `file_id` is dead. |
| `source_changed`  | session   | The file changed under the source mid-transfer; retrying must start over. |
| `user_cancel`     | session   | A human cancelled it. |
| `unknown_offer`   | session   | The pull named a `file_id` the source no longer offers. |
| `expired`         | session   | The offer's TTL elapsed before this transfer started. Gates the **start** only: a transfer already in flight keeps going (§3.4). |
| `busy`            | session   | The source is at its concurrency limit (`MAX_ACTIVE_PULLS`). The receiver may retry under a **new** `transfer_id`. |
| `window_too_large`| session   | The pull asked for more than `MAX_PULL_WINDOW`, or zero. Only the transfer is aborted; the connection stays open. |
| `invalid_start`   | session   | A session-less pull did not start at index 0, or the id named a different `file_id`, or the pull had no `from_device`. |
| `failed`          | n/a       | **Not a wire value.** A receiver-side mapping target for reasons this build does not recognise. Never emit it: doing so would rewrite a peer's unknown reason into a fabricated known one. |

Replies to a specific `file_pull` are always session-scoped and addressed to the
**puller**, not to the source that would have served them. A refusal sent to
`pull.to` would go to the wrong device and leave the receiver waiting for a
timeout.

### 3.9 `peer_changed` — a device joined or left

Sent by the **hub** only, to every connected peer, when a device's connection
appears or disappears. Together with `welcome.peers` it keeps each client's view
of the network current without polling.

```json
{
  "type": "peer_changed",
  "device": "22222222-3333-4444-8555-666666666666",
  "caps": ["lazy-file", "file-recv"],
  "event": "joined"
}
```

| Field   | Required | Notes |
| ------- | -------- | ----- |
| `device`| yes      | The peer's `device_id`. |
| `caps`  | optional | Capability tokens the peer advertised. Absent on a pre-0.4 peer. Unknown or malformed tokens are ignored, not an error: rejecting the frame would make this client unable to track membership merely because the hub grew a token grammar it does not know. |
| `event` | yes      | `"joined"` or `"left"`. Any other value fails deserialisation. |

A `left` event is *not* sent when a connection merely drops and may come back
within `DEVICE_GRACE_MS`; it marks a device that is gone for good. The `caps`
are carried on the `left` frame because the peer row is already deleted by the
time it is sent — a client diffing `welcome.peers` against a stream of
`peer_changed` would otherwise see capabilities change on the way out.

## 4. Security model

clipboardwire v0.4 has **no application-layer cryptography**. Confidentiality and
integrity on the wire come from TLS — terminated either inside the server
(`rustls`, when `CLIPBOARDWIRE_TLS_CERT_FILE` / `CLIPBOARDWIRE_TLS_KEY_FILE`
are set) or at a reverse proxy in front of it. The server processes plaintext
clipboard contents in memory; whether it logs them is constrained by §3.1.

| Threat                                  | Mitigated?                                                            |
| --------------------------------------- | --------------------------------------------------------------------- |
| Network attacker reads clipboard        | yes, via TLS (built-in `rustls` or a reverse proxy).                  |
| Network attacker tampers with clipboard | yes, via TLS.                                                         |
| Server operator reads clipboard         | **no.** Out of threat model.                                          |
| Server disk / RAM theft                 | **no.** `last_clip` lives in process memory; logs may contain frame metadata. |
| Replayed frames after reconnect         | mitigated: clients drop frames whose `ts` is older than the last applied `ts`. |
| Stolen Basic-auth credentials           | grants full read/write access; rotate the server password.            |
| Traffic analysis (sizes, timings)       | no.                                                                   |
| Corrupted file bytes from a buggy source | mitigated **only** against accidental corruption: the receiver verifies SHA-256. See the note on what that hash covers. |
| Malicious peer pulling every offered file | **no.** See the note on offer visibility.                          |
| Malicious peer exhausting hub memory with transfer ids | mitigated: `MAX_ACTIVE_TRANSFERS` bounds the session memory and evicts oldest-first (§5). |

### What the digest actually covers

`file_digest` (and an eager chunk's `file_sha256`) is the hash of **the byte
stream the source served**, not of the file currently on disk. A source that
reads a file while another process rewrites it can produce a digest that verifies
correctly against bytes no longer on the file system.

That gap is why identity is re-checked repeatedly rather than once: at every
window, and again immediately before a digest is emitted. If the underlying file
has changed in between — size, modification time, or inode — the source answers
`file_abort{source_changed}` instead of hashing a mixture of two versions. What
the protocol does **not** provide is a guarantee that the served bytes ever
corresponded to a file the user meant to send; that is the source implementation's
job, not the wire's.

### What an offer exposes, and for how long

An offer is a **standing promise**, not a one-shot notification. It lives until
`expires_at_ms` (default TTL: 30 minutes) or until the source goes away and its
grace period elapses. During that window:

- **any connected peer can pull the file** — not just the ones present when it was
  copied;
- a peer that connects *later* learns about it from `welcome.offers` and can pull
  it immediately, with no further action by the source;
- the source has no per-peer control: there is no way to say "only send this to
  my laptop". Authorization is one shared credential for the whole deployment.

In other words the exposure window of a file transfer is the offer TTL, not the
duration of the transfer. On a hub with more than one authenticated peer, a copy
publishes the file to all of them for thirty minutes. Deployments that cannot
accept that should raise `offer_ttl_minutes`… downward, or keep the hub
single-peer.

This is appropriate for a LAN- or VPN-only deployment on hardware the user owns.
A future protocol revision may introduce optional end-to-end encryption with
TOFU device pairing (similar to Signal Desktop's QR-code flow), at which point
the `clip` frame will gain `nonce` / `ciphertext` fields and `content` will
become mutually exclusive with them. The capability mechanism in §7 is the
upgrade hook that makes that deployable incrementally.

## 5. Limits

All values below are enforced in code; the constants are named so an
implementation can find them.

| Limit | Value | Where | Behaviour on breach |
| ----- | ----- | ----- | ------------------- |
| `MAX_FRAME_BYTES` | 50 MiB (52 428 800 B) | WS layer; tunable via `CLIPBOARDWIRE_MAX_FRAME` | `error{frame_too_large}` then close `4003`. |
| `MAX_CONNS` | 64 (default) | Server config; tunable via `CLIPBOARDWIRE_MAX_CONNS` | The upgrade is answered with HTTP `503`. |
| `MAX_OFFERS_PER_DEVICE` | 256 | Hub | The **new** offer is rejected. Other peers' offers are untouched. Never evicts. |
| `MAX_OFFERS_TOTAL` | 4096 | Hub | As above. Expired offers are swept first, so a rejection means "genuinely full of live offers". |
| `MAX_OFFER_TTL_MS` | 24 h | Hub | `file_offer` rejected as `BadExpiry`; the connection stays open. |
| `MAX_OFFER_NAME_BYTES` | 1024 | Protocol | Control-frame rejection (transfer-scoped). |
| `MAX_OFFER_CONTENT_TYPE_BYTES` | 255 | Protocol | Control-frame rejection. |
| `FILE_CHUNK_BYTES` | 4 MiB (4 194 304 B) | Protocol | Not a rejection bound: it is the chunk size the source reads. Wire size after base64 is ≈ 5.5 MiB, inside `MAX_FRAME_BYTES`. |
| `MAX_PULL_WINDOW` | 32 chunks | Protocol | `file_abort{window_too_large}`; only that transfer ends. `window: 0` gets the same answer. |
| `MAX_ACTIVE_PULLS` | 4 | Source (`PullServer`) | Further sessions queue for a batch-mate or are refused `busy`. Bounds open file handles and read buffers per source. |
| `MAX_ACTIVE_TRANSFERS` | 16 384 (= 4 × `MAX_OFFERS_TOTAL`) | Hub | At the cap, the oldest 2048 sessions (an eighth) are forgotten in one pass. Forgetting fails **closed**: a forgotten session's later windows are judged by the offer TTL again. |
| `TRANSFER_MEMORY_MS` | 30 min | Hub | A session nobody has pulled for this long is forgotten on the next tick. |
| `DEVICE_GRACE_MS` | 60 s | Hub | A device's offers are dropped and `file_abort{source_gone}` is sent. A reconnect inside the window cancels the sweep. |
| `MAX_CAPS_BYTES` | 512 | Protocol | The whole `caps=` value is ignored — equivalent to advertising nothing. Deliberately not truncated, so two implementations never disagree about where the cut falls. |

Two of these deserve a note because they are often mistaken for each other:

- `MAX_ACTIVE_PULLS` limits how many transfers a **source** reads concurrently.
  A receiver can have far more sessions open than that.
- `MAX_ACTIVE_TRANSFERS` limits how many session ids the **hub** remembers so
  that TTL can be applied per transfer rather than per frame. It is a hub memory
  bound, not a concurrency limit; nothing is refused because of it.

Server `last_clip` cache: in-memory only; one slot, last-write-wins. Lost on
process restart. Offers and transfer sessions are likewise memory-only — a hub
restart drops them, and clients cannot distinguish that from a connection loss.

## 6. Close codes

The server uses these WebSocket close codes (private range 4000–4999) plus
standard `1000`/`1001`.

| Code   | Name              | Meaning                                                       |
| ------ | ----------------- | ------------------------------------------------------------- |
| `1000` | normal            | Graceful shutdown initiated by either side.                   |
| `1001` | going away        | Server is shutting down.                                      |
| `4001` | unauthorized      | Reserved; auth failure normally surfaces as HTTP 401 before upgrade. |
| `4002` | bad_frame         | Malformed JSON, missing required fields, wrong field types, or a `file_chunk` that mixes the eager and lazy shapes. |
| `4003` | frame_too_large   | Frame exceeded §5 limit.                                      |
| `4004` | unsupported_type  | Reserved. Unrecognised `type` values are **ignored**, not fatal (§3); this code is not emitted for them. |
| `4005` | duplicate_session | Another connection presented the same `device_id`; the superseded one is asked to close. |

## 7. Versioning

This document is versioned with the server. Breaking changes bump the minor
version while < 1.0. The server advertises its build in `welcome.server`
(`clipboardwire/<major>.<minor>.<patch>`).

**Version differences downgrade capability; they do not refuse the connection.**
A client does not compare `welcome.server` against the version it was built for,
and a server does not reject a client for its version. `welcome.server` is
diagnostic: it belongs in a log line and a bug report, not in a branch.

What actually gates behaviour is `caps`:

- A client advertises `caps=` on the upgrade request. Absent or empty means "no
  optional capabilities", which is exactly what a pre-0.4 client looks like.
- The hub advertises `welcome.caps`. Absent means the same thing, and is how a
  v0.3 hub appears to a v0.4 client.
- A client decides *what it can do* from its own configuration, not from the
  hub's version: a sender offers files when its `send_mode` is `lazy`, and a
  receiver advertises `lazy-file` when its `receive_mode` can pull.
- The hub's `welcome.caps` **does** gate one decision on the sender side. A
  sender with `send_mode = "lazy"` publishes offers only if the hub advertised
  `lazy-file`; otherwise it streams eagerly and logs one warning per connection.
  The reason is that publishing into a hub that ignores `file_offer` looks
  successful while the file can never be pulled — an unknown frame type is
  ignored by design (§3), so there would be no error to report.
- The handshake window is covered by the same conservative default: until the
  first `welcome` arrives the capability set is empty, so a copy that races the
  handshake goes eager rather than offering into a hub that may not accept it.
- `peer_changed.caps` lets a peer react to a specific counterpart's capabilities
  without assuming anything from a version string.

Capability tokens are a comma-separated list of short ASCII tokens:

| Token         | Advertised by | Meaning |
| ------------- | ------------- | ------- |
| `lazy-file`   | client, hub   | Can consume `file_offer` and pull chunks on demand. |
| `file-recv`   | client        | Can receive file bytes at all (eager or lazy). |
| `transfer-id` | client        | Understands `transfer_id` as the session key. |

The grammar is deliberately open: unknown tokens are ignored on both sides, and a
malformed token is dropped rather than fatal — the same rule as unknown frame
types (§3). Adding a capability is therefore not a breaking change. Because the
token set is what both sides agree on, a hub that grows a token it cannot read
still works with clients that ignore it, and vice versa.

The practical consequence: **nothing on the wire refuses a connection for its
version.** A v0.4 client and a v0.3 hub connect to each other, exchange clips,
and transfer files eagerly. A v0.3 hub advertises no `caps` and sends no
`offers` (both fields are simply absent from its `welcome`), and — by the rule in
§3 — it ignores the `file_offer` frames a lazy sender would send. A v0.4 client
reading that `welcome` sees an empty capability set, which is the honest answer:
file transfer works, lazy transfer does not. Mixed deployments should configure
senders for `eager` rather than rely on the offers being ignored.

## 8. Out of scope

- Multi-user support (would need a per-user namespace on the URL and per-user
  fan-out maps). Authorization remains a single shared credential.
- Multi-file copy/paste *as a single clipboard object* — files are transferred
  individually and grouped only by `batch_id` for scheduling purposes.
- Push-style clipboard events on platforms that support them (we poll
  instead).
- File-based persistence for `last_clip` (nor for offers or transfer sessions).
- Resuming a transfer across a reconnect. A dropped connection loses the
  session; the receiver restarts from index 0 under a new `transfer_id`.
- Application-layer encryption / TOFU device pairing (see §4 for the future
  upgrade path).
